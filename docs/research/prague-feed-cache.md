## Bottom line

1. **The generator is entirely attribute-driven with exactly one exception** — it reads `build_property.RootNamespace` from `AnalyzerConfigOptionsProvider` (line 196). No additional files, no naming conventions, no interface scanning that isn't a fallback for a missing attribute. And of its fourteen attributes, only six are ones protop must emit at all — see §0.

2. **The hardest thing protop must model is the computed member.** 7 of the 16 Prague keys are get-only expression-bodied ValueTuples over two fields, and one index sits on a computed `int` — none of which is expressible as a protobuf field (§11.C). The hardest thing protop must *avoid* is not an attribute at all — it is the file itself. The generator's syntax predicate rejects any file whose path ends in `.g.cs` or `.generated.cs`, sits under `obj/`, `bin/` or `Generated/`, *or whose first 500 characters contain the string `auto-generated`* (lines 243–255). If praguec emits the hand-written half through a source generator, or with the conventional `// <auto-generated/>` banner, **`Prague.Feed.Cache` will silently generate nothing** — no error, no diagnostic, just a missing partial half and a wall of CS0246. See §8.

3. **`[DataCacheKey]` on a get-only computed ValueTuple is load-bearing in three separate ways, none of which the generator checks directly.** The generator itself is indifferent (§5). But `IDataCacheItem<TKey,TValue>` constrains `TKey : IEquatable<TKey>`, which is why a ValueTuple works and an arbitrary class would not; and the generated `Clone()` is an object initializer over public get+set properties, which is why the key must be get-only — a settable key would be assigned twice and the computed identity would drift.

4. **The generator never reads `[MessagePackObject]` or `[Key(N)]`.** Its only MessagePack interaction is one-way and conditional: if `MessagePack.IgnoreMemberAttribute` resolves in the compilation, it decorates its own emitted `__PragueMetadata__` property with `[MessagePack.IgnoreMember]` (lines 90, 6052–6055). §6.

5. **Class-level `[DataCacheIndex]` is dead code on a `[DataCache]` item type in 0.0.30.** It is only read inside `GenerateExternalCacheClass` (line 2048), the `[DataCache<T>]` path. The Prague code has exactly one such usage and it does nothing. §3.

6. **`[v:name]` is not parsed at compile time at all.** The template string is embedded verbatim as `public const string TopicNameTemplate = "<template>"` and resolved at runtime by a regex in the Kafka assembly. §7 documents the syntax — but see §0: the topic template is application configuration and does not belong in the protop format.

## 0. Scope — what protop owns, and what it does not

The protop format describes **cache items and the relationships between them**. It does not describe how a given application deploys them. That line falls in a convenient place, because C# lets **class-level attributes be split across partial declarations** while **member-level attributes cannot be** — a property is declared exactly once.

So the contract partitions cleanly:

| Attribute | Target | Owner | Why |
| --- | --- | --- | --- |
| `[DataCacheKey]` | property | **protop** | identity of the item — intrinsic |
| `[DataCacheIndex]` (member form) | property | **protop** | how the item is looked up — intrinsic to the item's shape |
| `[DataCacheForeignKey<T>]` | property | **protop** | a relationship between two items — the format's core business |
| `[DataCacheFromTimestamp]` | property | **protop** | marks the item's own versioning field |
| `[DataCacheHeader]` | property | **protop** | binds a member to transport metadata |
| `[DataCacheGlobalLastUpdateIndex<T>]` | property | **protop** | a relationship to an index type |
| `[DataCache]` / `CacheClassName` | class | **application** | names a per-app cache facade |
| `[DataCacheTopic]` + its `[v:…]` template | class | **application** | deployment/Kafka configuration |
| `[DataCacheSort]` | class | **application** | a query surface, not a data property |
| `[DataCacheIndex]` (class form) | class | **application** | and inert anyway on an item type — §3 |
| `[DataCacheIgnoreEquality]` | class **or** property | **split** — class form to the application, property form to protop | the property form is a statement about the member |
| `[DataCacheJsonSerializables]`, `[DataCacheFrom<T>]` | class | **application** | serialization wiring; and `[DataCacheFrom]` is a competing source-of-truth (§9) |

**Everything in the "application" column can stay in the hand-written partial half.** Class-level attributes on any partial declaration are merged by the compiler and seen by the generator through `INamedTypeSymbol.GetAttributes()`, which unions across declarations. That is *not* a speculative claim about protop — it is how `BOTicketTypeCache.cs` already works today, a second partial declaration of the cache class in a separate file (`BO/BO.Services/Prague/Models/BOTicketTypeCache.cs`).

The consequence is that **protop's passthrough problem reduces to member-level attributes only** — six attribute kinds, 36 occurrences in the Prague corpus. The rest of this document still catalogues the full surface, because protop must not *collide* with what the application half declares and must know what the generator emits; but sections 7 (topic templates) and the cache-class parts of section 4 are reference material about the surrounding system, not requirements on the format.

## 2. What the generator requires of the annotated type

### Required

| Requirement | Evidence | Failure mode |
| --- | --- | --- |
| **`partial`** | the generator emits `public partial class {Name} : …` for the same type in three separate files (lines 3089, 4125, and 4796 for the enrichable half) | plain compiler error CS0260 — **there is no generator diagnostic for this on an item type**; the `partial` check at line 1988 (`CACHE011`) applies only to a `[DataCache<T>]` cache class |
| **`public`** | all emitted halves are declared `public` (lines 3089, 4125, 639) | CS0262, conflicting accessibility modifiers |
| **`class` or `record`** (reference types only) | syntax predicate accepts only `ClassDeclarationSyntax` / `RecordDeclarationSyntax` (line 239); `IsRecord` selects `partial record` vs `partial class` (line 3088) | struct / record struct: never seen, no diagnostic |
| **top level, not nested** | `CACHE004` at line 531 (`CACHE010` for the external-cache variant) | reported diagnostic, error severity |
| **a usable parameterless constructor** | `Clone` is emitted as `return new {Type} { Prop = …, … };` — an object initializer (lines 3041–3057 of the helper builder) | CS1729 in the generated clone helper |
| **at least one `public` property with both a getter and a setter** | line 3076: `DeclaredAccessibility == Public && GetMethod != null && SetMethod != null`; if the count is zero, `GenerateCloneMethod` returns `null` | **silent** — no `Clone()`, no `IDataCacheItem<,>`, therefore no `IDataCache<,>` satisfaction downstream |
| **at least one `public` readable property not marked `[DataCacheIgnoreEquality]`** | line 4111, same early-`null` pattern | silent, as above |
| **key type implements `IEquatable<TKey>`** | `IDataCacheItem<TKey,TValue> where TKey : IEquatable<TKey>` in `Core/IDataCacheItem.cs` | constraint violation on the emitted interface |

`init`-only setters satisfy the get+set filter (`SetMethod` is non-null for `init`) and work inside an object initializer. `SlimShow` uses `public long Id { get; init; }` (`SlimShow.cs:16`) and compiles — **VERIFIED by usage, INFERRED as to mechanism** (the Roslyn `SetMethod.IsInitOnly` flag is never inspected by the generator).

### Not required

- **`sealed` is not required.** Prague uses it universally, but the generator emits no `sealed` on its own halves and has no diagnostic for its absence. It does *change behaviour*, twice:
  - **Clone strategy.** A non-sealed class with at least one derived type in the compilation gets a `ClonePolymorphic_{Name}<T>` dispatcher with a `switch` over every derived type and a `NotSupportedException` default (lines 2976–3028). Sealed types get a direct clone. Keeping Prague's types `sealed` is what keeps this cheap.
  - **Kafka registration.** `ExecuteKafkaExtensions` only registers a cache when `IsSealed || FindAllDerivedTypes(...).Count == 0` (line 4387). A non-sealed type with subclasses gets **no Kafka extension methods at all**, silently.
- **No base class, no interface.** `IDataCacheItem<TKey,TValue>` is *emitted onto* the type, not required of it. Implementing it by hand is only a **fallback** path for the key: `ExtractKeyInfo` looks for `[DataCacheKey]` first, then for an `IDataCacheItem<,>` in `AllInterfaces`, then defaults `TKey` to `string` (line 6489). In that fallback the register method calls `item.GetKey()` (line 6419) — a method not declared on `IDataCacheItem` in 0.0.30, so the fallback path appears **broken**; `[DataCacheKey]` is the only working route. **VERIFIED for the attribute path, UNVERIFIED that the fallback is unusable** (we did not attempt a compile).
- **Accessibility of members** is not checked beyond `public`; a `public` property with a `private set` passes the get+set filter and would then fail to compile inside the separate helper class. Edge case, not exercised by Prague.
- **Key property must be declared on the type itself.** `ExtractKeyInfo` calls `classSymbol.GetMembers()`, not a walk up the base chain. An inherited `[DataCacheKey]` is invisible.

## 3. Class-level `[DataCacheIndex]` is inert on a `[DataCache]` type

`GenerateCacheClass` (the `[DataCache]` path, line 506) collects indexes exclusively through `ExtractIndexedProperties`, which enumerates `GetMembers().OfType<IPropertySymbol>()`. The only `FindAttributes(cacheClassSymbol, "…DataCacheIndexAttribute")` call in the assembly is at **line 2048, inside `GenerateExternalCacheClass`** — the `[DataCache<TCacheItem>]` path, where the annotated class *is* the cache and the indexed properties live on a different type.

The Prague corpus contains exactly one class-level usage:

```csharp
// BO/BO.Services/Prague/Models/BOShowCacheItem.cs:13
[DataCacheIndex(nameof(ListingIdIndex), nameof(ListingId), DataCacheIndexType.Many)]
```

It is a no-op, and the codebase works around it twelve lines later with a member-level index on a computed property:

```csharp
// BOShowCacheItem.cs:93-95
[DataCacheIndex]
[IgnoreMember]
public int ListingIdIndex => ListingId ?? 0;
```

(Its argument order is also transposed relative to the `(propertyName, indexName, indexType)` constructor, which is further evidence nobody ever exercised it.)

**Consequence for praguec:** the class-level form must still be forwarded verbatim — it is legal C# and a future package version may start honouring it — but it must not be *relied upon*. Any index praguec is asked to produce must land on a member.

## 5. Is `[DataCacheKey]` on a get-only computed ValueTuple load-bearing?

The corpus, at `22331403` — 16 uses, **7 of them get-only computed ValueTuples**:

```csharp
// BOTicketTypeCacheItem.cs:22-24, and identically in BPTicketTypeCacheItem, Processors/…/TicketTypeCacheItem
[Key(0)]
[DataCacheKey]
public (long EventId, long TicketTypeId) Key => (EventId, TicketTypeId);

// BOSearchCacheItem.cs:17-18, BPSearchCacheItem, BrandReader/…/SearchCacheItem, Processors/…/SearchCacheItem
[Key(0)]
[DataCacheKey]
public (long EventId, Channel ChannelId) Key => (EventId, ChannelId);

// SlimTicketType.cs:42-44  — same shape, named Id rather than Key
[Key(0)]
[DataCacheKey]
public (long EventId, long TicketTypeId) Id => (EventId, TicketTypeId);
```

The other 9 are ordinary settable scalars (`public long EventId { get; set; }`, and one `public long Id { get; init; }`).

**Verdict, decomposed:**

| Question | Answer | Evidence |
| --- | --- | --- |
| Does the generator check that it is get-only? | **No.** | `ExtractKeyInfo` (line 6489) filters on the attribute alone — `GetMembers().OfType<IPropertySymbol>().FirstOrDefault(p => FindAttribute(p, "…DataCacheKeyAttribute") != null)`. No accessor inspection anywhere. |
| Does the generator check that it is a ValueTuple? | **No.** | It takes `p.Type.ToDisplayString()` as `KeyTypeName` and never examines the type's shape. |
| Does the property name matter? | **Only two names are special-cased.** | `keyPropertyName != "Key"` guards `With{KeyProperty}` emission (lines 1121, 1608, 6272), so a key literally named `Key` suppresses a duplicate helper. `Prague` uses both `Key` and `Id`, so both branches are exercised. |
| Is get-only-ness load-bearing *in effect*? | **Yes — decisively.** | `Clone` is emitted over public properties with **both** accessors (line 3076). A get-only key is excluded from the object initializer, which is the correct outcome: the clone reconstructs `EventId`/`TicketTypeId` and the computed key follows. Give the key a setter and it becomes a clonable property whose value is derived — the initializer would assign it, and on a ValueTuple with no setter body that is a compile error; on a settable key it is a silent duplication of identity. |
| Is the ValueTuple choice load-bearing? | **Yes — for a reason external to the generator.** | The emitted `IDataCacheItem<TKey,TValue>` constrains `where TKey : IEquatable<TKey>` (`Core/IDataCacheItem.cs`), and `IDataCache<TKey,TValue>` repeats it (`Core/IDataCache.cs`). `ValueTuple<long,long>` satisfies it; a composite key expressed as a plain class would not, unless it implemented `IEquatable<>` by hand. |
| Does it affect anything else? | **Two things.** | (a) `IsTypeParsable` (line 6544) checks for `IParsable<TSelf>`; a ValueTuple is not, so `public static bool IsKeyParsable => false` is emitted and the HTTP query surface loses key parsing. (b) The key property **is** included in `CacheEquals`/`CacheGetHashCode`, because the equality filter requires only a getter (line 3698) — so a computed key is compared redundantly alongside its components. Harmless, but not free. |

**A passthrough hazard worth flagging.** Prague puts `[Key(0)]` (MessagePack) on these get-only computed properties. MessagePack-CSharp can serialize a get-only member but cannot assign it on deserialize without a matching constructor parameter, and `SlimTicketType`'s constructor takes `ticketTypeId`/`eventId`, not `id`. Whether this round-trips, throws at formatter-generation time, or is quietly tolerated was **not verified** — it is outside this ticket's scope and outside the generator's. But praguec has to decide whether to emit `[Key(N)]` on a computed key at all, and the answer is not obviously "yes, because Prague does".

## 6. MessagePack interaction

**The generator does not read `[MessagePackObject]`, `[Key(N)]`, `[IgnoreMember]`, or any other MessagePack attribute.** Exhaustive grep over the decompiled generator finds exactly three MessagePack touchpoints:

1. `CompilationContext.HasMessagePack = compilation.GetTypeByMetadataName("MessagePack.IgnoreMemberAttribute") != null` (line 90) — a *presence probe on the type name*, not on any usage.
2. If that probe is true, `GeneratePragueMetadataAndClone` prefixes its emitted `__PragueMetadata__` property with `[MessagePack.IgnoreMember]` (lines 6052–6055). Same for `[JsonIgnore]` under `HasSystemTextJson`.
3. The Kafka header path calls `HeadersSerDe.SerializeMessagePack` / `TryDeserializeMessagePack` for `[DataCacheHeader]` properties (lines 4674, 4765) — runtime, and only for the header feature Prague does not use.

The references at lines 1092, 1121, 1608, 2393, 2422 and 6272 that grep for `"Key"` are comparing a **property name**, not an attribute. They are unrelated.

So: **the generator is fully independent of MessagePack.** The two are orthogonal decorations on the same type, coupled only by the one conditional `[IgnoreMember]` above. praguec can choose MessagePack key assignment without consulting the cache contract at all — and vice versa.

## 7. The topic model and the `[v:…]` placeholder syntax

### Compile time: verbatim, unescaped

`ExtractTopicName` (line 6504) reads constructor argument 0 of `[DataCacheTopic]` as a raw string, defaulting to `"Cache." + {TypeName}` when the attribute is absent or has no argument. That string is then embedded directly into the generated cache class:

```csharp
// CacheGenerator.cs:937-938
sb.AppendLine("        public const string TopicNameTemplate = \"" + text2 + "\";");
sb.AppendLine("        public string TopicTemplate => TopicNameTemplate;");
```

**There is no escaping.** A template containing `"` or `\` produces malformed generated code. There is no validation of placeholder syntax, no diagnostic for an unknown variable, and no parsing of any kind. Whatever praguec writes is what lands in the const.

### Runtime: two regexes, in the Kafka assembly

`Prague.Feed.Cache.Kafka.Internal.ConfigTools` (decompiled from `Prague.Feed.Cache.Kafka.dll`):

```csharp
private static readonly Regex _envRegex = new Regex("\\[e:(\\w+)\\]", RegexOptions.Compiled | RegexOptions.NonBacktracking);
private static readonly Regex _varRegex = new Regex("\\[v:(\\w+)\\]", RegexOptions.Compiled | RegexOptions.NonBacktracking);

public static string BuildConfigValue(IReadOnlyDictionary<string, string> vars, string value)
    => ReplaceEnvValues(ReplaceVarValues(vars, value.Trim()));
```

Called from exactly one place — `KafkaCacheHandlerBuilder.Build`, line 263:

```csharp
string topic = ConfigTools.BuildConfigValue(
    vars,
    _topicNameResolver == null ? ((IDataCache)cache).TopicTemplate : _topicNameResolver(sp));
```

**The syntax, precisely:**

| Form | Meaning | Source |
| --- | --- | --- |
| `[v:name]` | substitute from the `Vars` dictionary | `KafkaCachesOptions.Vars` (`Dictionary<string,string>`, `init`-settable — i.e. bound from configuration) |
| `[e:NAME]` | substitute from `Environment.GetEnvironmentVariable(NAME)` | process environment |

Semantics, all verified from the regex and the two `Replace` delegates:

- The identifier is `\w+` — ASCII letters, digits and underscore only. **No dots, no hyphens.** `[v:brand-id]` would not match and would be left in the topic name verbatim.
- **Lookup is case-sensitive** (`vars.TryGetValue`, default `Dictionary<string,string>` comparer). `[v:brandId]` and `[v:BrandId]` are different variables.
- **An unresolved placeholder is left literally in place** (`return m.Value`), not blanked and not an error. A typo produces a Kafka topic literally named `Cache.[v:brandid].TicketType`.
- **Order is vars first, then environment.** A var *value* containing `[e:X]` **is** subsequently env-expanded; an env value containing `[v:x]` is **not** re-expanded. One level of chaining, one direction only.
- The whole value is `.Trim()`ed before substitution.
- Placeholders may appear anywhere and any number of times; the regex is a global replace.

Prague uses a single variable, `brandId`, in all 16 topics: `Cache.[v:brandId].TicketType`, `Cache.[v:brandId].LiveObject`, `Cache.[v:brandId].Search`, `Cache.[v:brandId].Show`.

### 8.1 The file-level exclusion — the single most important finding for praguec

`IsSyntaxTargetForGeneration` (lines 230–256) rejects a candidate before any semantic analysis if **any** of the following holds:

```
filePath contains  "\obj\"  "/obj/"  "\bin\"  "/bin/"  "\Generated\"  "/Generated/"
filePath ends with ".g.cs"  or  ".generated.cs"
the first 500 characters of the file text contain "auto-generated"
```

and separately requires the node to be a `ClassDeclarationSyntax` or `RecordDeclarationSyntax` carrying at least one attribute list.

The generator's own output carries `// <auto-generated/>` as line 1 of every emitted file (lines 3082, 4119, and every other emission site), which is how it avoids recursing on itself.

**This makes the delivery mechanism part of the contract.** Three concrete constraints on praguec:

1. praguec's output **cannot be a Roslyn source generator that runs in the same compilation** — generator-to-generator chaining is not supported by Roslyn anyway, but even setting that aside, `.g.cs`-suffixed output is excluded by name.
2. praguec must emit **checked-in, compiled-as-normal `.cs` files** with paths that avoid `obj/`, `bin/` and any directory segment literally named `Generated`.
3. praguec **must not emit the conventional `// <auto-generated/>` header**, nor any comment containing the substring `auto-generated`, in the first 500 characters. This is uncomfortable — that header is exactly what suppresses analyzers and style rules on generated code — so praguec will need a different suppression strategy (`#pragma warning disable`, a `.editorconfig` path glob, or `<ExcludeFromCodeCoverage>`), applied *after* the first 500 bytes or by a mechanism that is not a comment.

The `buildTransitive/Prague.Feed.Cache.Codegen.props` reinforces this: it appends `Generated\**` to `DefaultItemExcludes`, and only sets `EmitCompilerGeneratedFiles` when `PragueCacheShowGeneratedFiles == 'true'`. The `Generated/` directory is the package's own debug-output convention.

## 9. `[DataCacheFrom<T>]` — an analyzer, not a generator

Not used by Prague, but part of the surface and relevant because it *rewrites user source*. `DataCacheFromAnalyzer` raises:

- `DATACACHE001` (Info) — "`Class '{0}' has [DataCacheFrom<{1}>] but properties have not been generated yet`"
- `DATACACHE002` (Warning) — "`Source type '{1}' has changed since properties were generated for '{0}'`"

`DataCacheFromCodeFixProvider` then copies properties from `TSource` into the annotated class as real source text, honouring `Exclude`, `Only`, and `CopyAttributes` (default `true`, line 120) — and when `CopyAttributes` is on it rebuilds each source property's attribute list verbatim (`BuildAttributeList`, line 233). The `SourceHash` constructor argument is the staleness token.

**Relevance to praguec:** this is a competing source-of-truth mechanism. If a praguec-generated type were ever also `[DataCacheFrom<T>]`, the code fix would write into praguec's output file. They must not be combined; praguec should treat `[DataCacheFrom]` as forwardable-but-discouraged.

## 10. Diagnostics the generator can raise

Useful as a checklist of what praguec's output must not trip. All are `DiagnosticSeverity.Error` and category `CacheGenerator` (except `CACHE005`–`CACHE007`, category `DataCache`).

| `CACHE002` / `CACHE016` | `Range`-indexed property is not `IComparable<T>` or a built-in comparable |
| `CACHE004` / `CACHE010` | cache type nested inside another type |

| `CACHE008` | `[DataCacheForeignKey<T>]` where `T` lacks `[DataCache]` |

## 11. What this means for protop's attribute passthrough

Read this with §0 in hand: protop describes **items and their relationships**, so only the six member-level attributes are its problem. Topic templates, cache class names, sorts and query surfaces are application configuration and live in the hand-written partial half.

**A. The passthrough problem is member-level attributes, and only those.** `[DataCacheKey]`, `[DataCacheIndex]`, `[DataCacheForeignKey<T>]`, `[DataCacheFromTimestamp]`, `[DataCacheHeader]` and `[DataCacheGlobalLastUpdateIndex<T>]` all target `Property`. A C# property is declared exactly once across a partial type, so these cannot be pushed into a companion file — they must be emitted on protop's own property declarations. Every class-level attribute can be, and should be, left to the application. `ExtractIndexedProperties`, `ExtractKeyInfo`, `ExtractForeignKeyProperties` and `ExtractGlobalLastUpdateIndexProperties` all enumerate `IPropertySymbol` members of the declaring type, confirming there is no companion-file escape for them.

**B. Passthrough must be syntactic and lossless, not semantic.** The generator matches attributes by fully-qualified display name and reads constructor arguments positionally, named arguments by string key. protop must reproduce exactly: the attribute's namespace-qualified identity, the *order* of positional arguments, the spelling of named arguments, and the literal text of every argument. It does not need to understand any of them — and should not try, because the argument grammar is the package's, not protop's, and will drift between versions.

**C. Some members protop must emit are not fields at all.** Two of the six member-level attribute kinds sit on *computed get-only properties* in the real corpus:

```csharp
[DataCacheKey]   public (long EventId, long TicketTypeId) Key => (EventId, TicketTypeId);
[DataCacheIndex] public int ListingIdIndex => ListingId ?? 0;
```

Neither is expressible as a protobuf field. protop needs a construct for "a derived member with an expression body, carrying attributes" — a computed-member escape hatch. **This is the hardest requirement in the contract**, and it is harder than it looks: the expression body references other members by name, so it is not opaque text — it has to survive protop's own naming and nullability decisions. A composite key is the *normal* case here, not an edge case: 7 of the 16 Prague keys are computed ValueTuples over two fields.

**D. The key is the one member whose semantics protop cannot ignore.** It must be get-only if computed (§5 — otherwise the generated `Clone()` object initializer assigns a derived value), its type must implement `IEquatable<>` (the `IDataCacheItem<TKey,TValue>` constraint — which is exactly why ValueTuple is the idiom), it must be declared on the type itself and not inherited, and it must not carry a `Many` index (`CACHE021`/`CACHE022`). Everything else protop forwards blind; this one it has to model.

**E. Relationships are the format's real content, and `[DataCacheForeignKey<T>]` is how they surface.** It is generic over the target item type and takes a `DataCacheJoinType` (`OneToOne` / `OneToMany`). The generator validates that `T` carries `[DataCache]` (`CACHE008`) and that the annotated property's type equals the referenced cache's key type (`CACHE009`) — so a protop relationship must resolve to the *target item's key type*, not to the target item itself. Prague does not use this attribute today, which means protop is free to design the relationship model rather than retrofit one.

**F. Emitted-name reservations.** protop must never emit, on a cache item type: `__pragueMetadata__`, `__PragueMetadata__`, `SetPragueMetadata`, `Clone`, `CacheEquals`, `CacheGetHashCode`, `CacheEqualityComparer`, `CacheEqualityComparerImpl`. Nor, in the item's namespace: `{TypeName}Cache` (the default cache class name) or `{CacheClassName}QueryParser`. The cache class itself protop does not emit — but it must not squat on its name.

**G. Shape requirements protop satisfies structurally, by forwarding nothing.** `public sealed partial class`, top level, with a public parameterless constructor and at least one public get+set (or get+init) property. Three of those five protop would do anyway; **the parameterless constructor and `partial`** are the ones to write into the spec explicitly, because their absence produces raw compiler errors from a *generated* file with no diagnostic pointing at the cause. `sealed` is not required but should be emitted: it keeps clone generation off the polymorphic-dispatch path and keeps Kafka registration from silently skipping the type (§2).

**H. Delivery mechanism is part of the contract.** See §8.1 — output file naming and the absence of an `auto-generated` banner in the first 500 bytes are hard requirements, not stylistic choices. protop's output files must not end in `.g.cs` or `.generated.cs`, must not sit under `obj/`, `bin/` or `Generated/`, and must not contain the substring `auto-generated` in their first 500 characters. Violating any of these makes `Prague.Feed.Cache` skip the type in silence. This is the constraint most likely to be discovered late and painfully, and it is worth an explicit test in protop's own suite.

**I. MessagePack and the cache contract are orthogonal.** Nothing in protop's MessagePack key assignment needs to consult the cache attributes, or vice versa — with the single open question in §5 about `[Key(N)]` on a get-only computed key.

**J. Two things protop should decline to forward.** Class-level `[DataCacheIndex]` is inert on an item type in 0.0.30 (§3) and belongs to the application anyway. `[DataCacheIndex(IndexName = …)]` is read through a non-existent member name and is silently dropped (§1.1) — protop should not offer custom index names until the package fixes it.

## Open questions

1. **Does MessagePack-CSharp round-trip `[Key(0)]` on a get-only computed property?** Prague does this on seven types. If it does not, those `[Key(0)]` annotations are noise at best and a latent deserialization failure at worst, and praguec should not reproduce them. Requires a compile-and-run test, not decompilation.
2. **Is the `IDataCacheItem<,>` key fallback actually usable?** The generated register method calls `item.GetKey()` for that path, and `GetKey` is not on the interface in 0.0.30. Probably dead; worth one compile to confirm, since it would otherwise look like a legitimate alternative to `[DataCacheKey]`.
3. **Which version should praguec target?** 0.0.30 is what Prague pins, but the local NuGet cache holds 34 versions up to `0.1.5-pre.30`. The `Name`-vs-`IndexName` bug (§1.1) and the inert class-level index (§3) are both the kind of thing a later version fixes — which would change the contract. A diff of 0.0.30 against the newest pinned-anywhere version is a cheap follow-up.
